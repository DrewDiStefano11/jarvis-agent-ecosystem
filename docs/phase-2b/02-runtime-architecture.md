# 02 - Runtime Architecture

This document defines the proposed runtime architecture for the Phase 2B autonomous worker. It identifies how the worker integrates with the existing Phase 2A control plane while remaining distinct from the deterministic simulation engine.

## Recommended Directory Structure

This structure builds upon the existing `apps/api/app` directory without modifying existing files:

```text
apps/api/app/
├── orchestration/       # Task claiming, lease management, worker loops
├── models/providers/    # LLM provider abstractions (OpenAI, Ollama, fake)
├── tools/               # Tool registry and implementations
├── policies/            # Permission models, risk assessment, policies
├── workers/             # The state machine and lifecycle for autonomous agents
├── validation/          # Review and structural validation of model output
└── scheduling/          # Continuous operation polling and backoff logic
```

## Request and Task Flow

1. **Intake:** A user submits a task via the existing FastAPI API. The task is durably persisted to SQLite (Phase 2A behavior).
2. **Polling:** The headless Worker Manager continually polls the database for unassigned, high-priority tasks.
3. **Claiming:** The Worker Manager claims a task using an atomic transaction, establishing a time-bound lease.
4. **Planning:** The Worker delegates the task to the Planner, which constructs a prompt and contacts the Local Model Provider.
5. **Validation:** The model returns a JSON-structured plan. The Validator confirms schema correctness.
6. **Execution:** The Executor iterates over the plan. For each step:
   - Tool requests are checked against the Policy Engine.
   - Allowed read-only tools are executed.
   - Risky tools are paused pending explicit human approval (stored in the database).
7. **Checkpointing:** Progress and state are written to SQLite after every significant transition or tool execution.
8. **Completion:** Upon successful validation of the final step, the task is marked completed, and an artifact is generated.

## Component Definitions

### Existing in Phase 2A
* **Database (SQLite & SQLAlchemy):** Persists tasks, audits, approvals, checkpoints, outbox events.
* **Simulator Engine:** The existing deterministic workflow. **Crucially, this remains entirely separate from the real worker.**
* **API Endpoints:** Task submission and status querying.
* **Outbox/WebSockets:** Event dispatching.

### Extended in Phase 2B
* **Approval Service:** Expanded to handle policy-driven risk levels generated by real tools.
* **Audit Service:** Extended to capture actual LLM tokens, prompts, and tool boundaries.

### New in Phase 2B
* **Worker Manager:** The orchestration layer responsible for lifecycle management, lease renewal, and queue polling.
* **Worker Process:** The state machine driving task execution.
* **Model-Provider Adapter:** The unified interface for OpenAI, Ollama, and LM Studio.
* **Planner & Executor:** The logic that queries the model, decodes JSON, and executes tools.
* **Validator:** Verifies model output against expected schemas and constraints.
* **Policy Engine:** Enforces the tool security boundary (read-only vs. risky).
* **Process Supervisor:** Windows/OS-level supervision to keep the manager running.

## Worker Process Placement Strategy

**Recommendation:** For Phase 2B, the Worker should run as a **background task managed within the same FastAPI process** (using `asyncio.create_task` tied to application lifecycle) or as a deeply coupled sidecar script, prioritizing local reliability and simplicity.

**Justification:**
1. The goal is local Windows deployment for a single user.
2. In-process or single-process deployment avoids the complexity of distributed systems, message brokers, and inter-process communication serialization.
3. SQLite operates best when concurrency is strictly managed. An in-process worker utilizing the same SQLAlchemy `UnitOfWork` setup ensures we do not encounter unnecessary `database is locked` errors during early autonomy. Future phases can extract this to a separate process as workload demands scale.
