# Phase 2B: Autonomous Worker Design Package

## Purpose of this Package
This package provides a comprehensive, implementation-ready design for Phase 2B of the Jarvis Agent Ecosystem. The purpose of this documentation is to allow a future implementation task to build Phase 2B without making major architectural decisions during coding.

> **Warning:** These documents are design specifications. They do not represent implemented functionality. Phase 2B code has not yet been written.

## Phase 2B Summary
Phase 2B introduces the first real, headless, persistent autonomous worker powered by a locally hosted open-source language model. It establishes a minimal safe runtime capable of continuously processing approved local tasks while preserving Phase 2A's durability, auditability, recovery behavior, and permission boundaries.

### What Phase 2B Adds
- A real headless local worker process that continuously polls for tasks.
- A local-model provider abstraction (with OpenAI, Ollama, and LM Studio compatibility).
- Atomic task claiming and leases suitable for SQLite.
- Structured planning and safe step execution using validated JSON.
- A strict permission and tool-boundary model.
- Robust checkpointing for resuming interrupted work.
- Worker observability, health checks, and a daily summary.

### What Phase 2B Intentionally Excludes
- Multi-agent delegation.
- General unrestricted capabilities (shell execution, Git pushes, arbitrary file mutation, email sending, browser automation).
- Remote access, multi-host coordination, or production cloud deployment.
- Voice control or complex desktop UI modifications.
- Self-modifying code or privilege expansion.

## Key Terms
- **Worker:** A persistent process or routine responsible for claiming, planning, and executing tasks autonomously.
- **Lease:** A durably recorded time-bound claim on a task to prevent concurrent execution.
- **Provider:** The local API endpoint representing the language model (e.g., Ollama, LM Studio, or a generic OpenAI-compatible endpoint).
- **Plan:** A structured sequence of steps generated by the model to achieve a task.
- **Checkpoint:** A saved point in execution that allows safe resumption without repeating non-idempotent work.
- **Tool:** A highly scoped capability granted to the model, governed by strict permissions.
- **Approval:** Human authorization required before executing risky actions.

## Major Safety Principles
1. **Model Output is Untrusted:** Every response from the model must be structurally and semantically validated before execution.
2. **SQLite remains Authoritative:** All state changes must be durably recorded. In-memory state is transient.
3. **Strict Tool Boundaries:** Unknown tools are rejected; the model cannot modify its own permissions or approval policies.
4. **Resilience Over Speed:** Safe recovery from crashes takes precedence over performance optimization.
5. **Human in the Loop for Risk:** Any capability beyond safe read-only operations requires pre-approved human authorization.

## Relationship to Phase 2A
Phase 2A established the foundational persistent control plane using FastAPI and SQLite (tasks, workflows, audit logs, outbox events, checkpoints, and safe restart recovery). Phase 2B directly consumes Phase 2A's persistent data models and audit facilities to power real (rather than simulated) work, extending but not replacing the Phase 2A foundation. The deterministic simulator from Phase 2A remains explicitly separate from the real worker.

## Relationship to Later Phases
Phase 2B aims to deliver one highly reliable worker rather than a swarm of unreliable agents. Later phases (such as Phase 2C or Phase 3) will introduce multi-agent delegation, remote PostgreSQL persistence, distributed scheduling, advanced continuous operation, and riskier capabilities (Git pushes, browser automation) once Phase 2B's foundation proves reliable.

## How Implementers Should Use the Package
Implementers should follow the [Jules Task Breakdown](18-jules-task-breakdown.md) and [Implementation Sequence](15-implementation-sequence.md). They should implement contracts first, followed by the test/fake provider, the worker loop, and finally the local model integration. This documentation should be referenced to resolve edge cases around error handling, crashes, and concurrency.

## Current Assumptions
- Development targets Windows primarily, utilizing local storage.
- SQLite acts as the durable authority; WAL mode and brief busy timeouts handle concurrency for a single machine.
- The model runs locally and handles structured responses (JSON schema) reasonably well.
- The user operator can resolve approval blocks manually.
